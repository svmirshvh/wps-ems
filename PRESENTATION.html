Requirements Interpretation

What the Brief Asked For

Core Business Problems

  • Excel forms lost, emailed inconsistently, no audit trail
  • Manual FX conversion prone to error; rate changes mid-process
  • No visibility for Finance until claim lands in inbox
  • Mobile employees photographing receipts — no structured upload
  • No enforcement of approval chain before payment

Non-Negotiables

  • WPS corporate email domain login only
  • Multi-currency: USD · EUR · TRY · CNY → AED
  • JPEG / PNG / HEIC / PDF receipt uploads
  • Client-side image compression before upload
  • Mobile-first (iOS Safari + Android Chrome)

Scope I Identified

  • 4-role RBAC: Employee · Manager · Finance · Admin
  • Claim lifecycle: Draft → Submitted → Manager Approved → Finance Approved → Paid
  • PDF generation matching the Excel layout exactly (categories A–G)
  • Finance dashboard with KPIs, CSV & Excel export
  • Email notifications at every state change
  • Full audit log — who did what, when, at what FX rate
  • Claim immutability once submitted; Finance can reopen rejected
  • PWA manifest for add-to-home-screen on mobile

Core Business Logic

Currency Conversion & FX Rate Handling

Four Source Currencies → AED

EUR
4.31 (Excel formula)

0.1065
CNY
0.5045

Critical Design Decision: Rate Freezing

When a claim is submitted, the FX rate used for each line item is frozen and stored alongside the amount. If rates change the next day, the claim amounts never change. This matches the auditability requirement and mirrors the Excel behaviour.

Fields: exchangeRateUsed, aedAmount, eurAmount — all stored as Decimal on ClaimItem.

EUR = AED ÷ 4.31

The original Excel file uses a fixed EUR formula. This was preserved exactly — every AED total is divided by 4.31 to produce the EUR equivalent shown on the claim form and in the generated PDF.

Live example
USD 500 × 3.6725 = AED 1,836.25
AED 1,836.25 ÷ 4.31 = EUR 426.04

Real-time preview on form

As the employee types an amount and selects a currency, the AED equivalent updates immediately on screen before saving. The rate used is fetched from the DB, shown inline next to the amount.

Security & Access Control

Security Model & RBAC

4 Roles with Strict Boundaries

EMPLOYEE Own claims only · Cannot approve
MANAGER Approve / reject SUBMITTED claims
FINANCE Final approval · Mark paid · Reopen · Export
ADMIN User management · Audit logs · All access

JWT Authentication

  • Access token: 15-minute expiry (stateless)
  • Refresh token: UUID stored in DB, 7-day expiry
  • Refresh tokens are revocable (logout invalidates)
  • Auth state persisted to localStorage via Zustand

Corporate Domain Restriction

Login is restricted to @wps.ae and @wps.local domains. Any other email is blocked at the backend with a clear error — configurable via env variable ALLOWED_EMAIL_DOMAINS.

Sensitive Data Handling

  • IBAN, SWIFT, bank details come from user profile — never free-typed on each claim
  • Receipts stored in private Supabase bucket — accessible only via time-limited signed URLs (1 hour)
  • Passwords hashed with bcrypt (12 rounds)
  • All API routes guarded by JWT — no public endpoints except login

Audit Trail

Every action — login, claim create/submit/approve/reject, receipt upload — is logged to an immutable AuditLog table with user ID, timestamp, IP, and metadata. Finance and Admin can view the full log.

Key Features

Mobile Experience & PDF Generation

📱 Mobile-First Design

  • Responsive breakpoints — all pages have dedicated mobile layouts (card list vs. table, stacked forms)
  • PWA manifest — add to home screen on iOS & Android without an App Store
  • HEIC accepted — iPhone photos don't need conversion by the user
  • Client-side compression — images compressed to ≤1.5MB, max 2000px before upload (saves data on mobile)
  • Image lightbox — tap thumbnail to see full-size receipt preview
  • Upload retry — 3 attempts with 1.5 s backoff for flaky connections

🔒 Autosave & Draft Protection

  • Form data backed up to localStorage every 60 seconds
  • Restored automatically on next visit if unsubmitted
  • Browser "leave page?" warning if form has content
  • Draft claims saved to server via "Save Draft" button

Status Enum

DRAFT SUBMITTED MANAGER_APPROVED FINANCE_APPROVED PAID REJECTED

Key Design Decisions

  • Soft deletes — deletedAt field, no hard deletes
  • Decimal type for all money — no floating point errors
  • Claim totals recalculated on every item add/remove/edit
  • RefreshToken table — server-side revocability
  • AuditLog — append-only, never updated

Claim Number Format

WPS-2026-0001
Year + zero-padded sequential counter. Unique, human-readable reference for Finance.

Assumptions & Considerations

Decisions Made in Absence of Full Spec

Assumed — Would Confirm Before Production

  • EUR = AED ÷ 4.31 — preserved exactly from the Excel formula; in production the rate would likely be a live feed
  • wps.local domain used for prototype; production would be @wps.ae
  • Manager role optional — brief says "may be required"; included it as it's best practice
  • Single approver per stage — could be multiple managers in production
  • Event name required — inferred from the * on the Excel form

Out of Scope (Noted)

  • HEIC → JPEG conversion — HEIC accepted and stored; full conversion needs a server-side library (sharp)
  • Receipt images embedded in PDF — PDF shows the claim form; receipts are separate attachments
  • SSO / Microsoft Entra — brief mentioned it, I used custom JWT as instructed
  • Localization (Arabic) — UI is English; i18n framework can be added

Technical Trade-offs Made

Modular monolith over microservices — easier to deploy, debug, and scale for this team size. Services can be split later.
Puppeteer over jsPDF/PDFKit — much easier to replicate complex table layouts from HTML; heavier but only runs on the server.
Supabase connection pooler (port 6543) — direct PostgreSQL (5432) blocked on some networks; pooler is more resilient.
localStorage autosave over server-side drafts — items are added to the server on submit, not on save; localStorage bridges the gap for form recovery.
getValues() not watch() in effects — avoids subscribing to every keystroke for autosave intervals; significant performance difference on large forms.

Deployment Guide

Go Live in 6 Steps

1
Deploy Backend to Railway
railway.app → New Project → Deploy from GitHub → select wps-ems/api
Set env vars: DATABASE_URL, SUPABASE_*, JWT_*, RESEND_*, FRONTEND_URL
Railway auto-detects NestJS and assigns a public URL.
2
Deploy Frontend to Vercel
vercel.com → New Project → Import GitHub → select wps-ems/web
Set: NEXT_PUBLIC_API_URL=https://your-api.railway.app/api/v1
Vercel handles build, CDN, and HTTPS automatically.
3
Update CORS & Email Config
In Railway env: set FRONTEND_URL=https://your-app.vercel.app
In Resend: verify your sending domain (e.g. noreply@wps.ae)
Update RESEND_FROM_EMAIL and FINANCE_EMAIL
4
Run Database Migration
Supabase project is already running. From your terminal:
cd api && npx prisma migrate deploy
This applies all migrations to the production Supabase DB.
5
Seed Initial Users
npx prisma db seed
Creates the Finance, Admin accounts with secure passwords. Employees are added via Admin panel — no public registration.
6
Custom Domain (Optional)
In Vercel: Settings → Domains → add expense.wps.ae
Point your DNS A record to Vercel's IP. HTTPS cert provisioned automatically.
Update ALLOWED_EMAIL_DOMAINS=wps.ae in Railway.
⏱ Estimated time: ~20 minutes
Both Railway and Vercel have free tiers sufficient for a pilot deployment.
